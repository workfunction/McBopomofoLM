# 0c D512 reranker 評估報告

日期：2026-10-13。問題是：0c（靈犀注音）公開的 D512 模型放進 McBopomofoLM 會不會比較好？0c 有哪些功能是我們沒有的？

**結論（分兩種用法）：**

- **放在 decoder 的位置（reranker）：不導入。** D512 單獨取代我們的 decoder 時沒有比較好。疊在現行 decoder 上有小幅、顯著的提升：新測試集聊天 +0.15pt、新聞 +0.25pt。但聊天組沒達到事先定的 0.2pt 門檻，而導入要多跑一個 130 MB 的 runtime，所以不值得。這個用法下真正有效的改進是讓 decoder 整句打分，加上補「再」雙胞胎詞，詳見同目錄的 [README.md](README.md)。
- **拿掉 encoder 和詞庫斷詞、只用 D512 解碼（第 4.6 節，事後追加的測試）：** 聊天組跟我們建議的設定 D 打平（96.44% 對 96.44%），新聞組明顯更好（97.53% 對 96.39%，+1.14pt）。D512 不受 encoder 前 3 名和詞庫斷詞限制時，實力比放在 decoder 位置時強得多。但要上線，必須先解決每按一鍵的延遲（需要 KV cache 和 ANE），也得重新接上小麥注音的使用者詞庫和選字記憶，所以建議的下一步是「兩案並陳」的混合版（第 5 節）。

## 1. D512 是什麼

| | |
|---|---|
| 模型 | `Funmula/0c-sequence-d512`，固定版本 `d512-pf512-20260926`，授權 MIT |
| 架構 | causal Transformer decoder，8 層、寬度 512、8 heads、FFN 768，共 32.6M 參數（ModernBERT 系的元件） |
| 檔案 | ONNX，130,723,134 bytes，SHA-256 `71af1f0e…`，只在 CPU 上跑（onnxruntime） |
| 輸入 | 已確認的前文（最多 64 字）＋注音（2 到 32 個音節）＋候選字串（最多 16 個，每個音節一字）。輸出 log P(候選 \| 前文, 注音) |
| 字表 | 27,857 字、416 個聲韻母組合、5 個聲調 |
| 訓練資料 | 新聞和財經論壇，共 12.45 億個漢字，都在 2026-09-01 之前 |
| 用法 | 自己不產生候選，要由引擎提供候選和引擎分數。融合分數 = 引擎分數 + w·模型分數，官方建議 w = 2、τ = 0。換到別的引擎要重新校正 |
| 另一個模型 | 標點模型 `Funmula/0c-punct-d512`（雙向 encoder，MIT），送出時自動補，。？！、；，F1 0.82 |

0c 論文裡的數字：在他們自己的三天新聞測試上，D512 系統 86.03%，小麥注音 67.17%。這個數字不能拿來比：

- 題目一半是刻意挑的難同音詞。
- 每題整段全對才算對。
- 測小麥注音時只給前幾個音節當前文，D512 卻有 64 字的已確認前文。
- 19 個百分點的差距裡，約 9.7 個來自他們自己的統計引擎（bigram 有用新聞資料調整過），D512 本身只貢獻 9.2 個。
- 測試集沒有公開。

## 2. 0c 有、我們沒有的功能

| 功能 | 能不能直接拿來用 |
|---|---|
| 送出時自動補標點 | 可以，模型公開（MIT）。**是唯一值得另外評估的項目** |
| Tab 補完 | 模型沒公開。我們 decoder 的 n16 到 n96 next-token 函式理論上可以做 |
| 模糊音（ㄗ/ㄓ、ㄘ/ㄔ、ㄙ/ㄕ、ㄣ/ㄥ） | 規則，可以自己做 |
| 中英混打 | 沒公開 |
| 按 `=` 叫出 emoji／顏文字選單 | 規則，可以自己做 |
| Windows／Linux | 不適用 |

反過來，我們有而 0c 沒提到的：打錯讀音的修正候選窗、看得到整串注音的雙向 encoder、在 ANE 上執行。

## 3. 怎麼接進來測

在我們的流程裡，D512 能放的位置就是現在 decoder 的位置。walk 選出的每個節點，如果有 2 個以上同長度的候選，就取 encoder 的前 3 名，算 b = enc + λ·D512 分數；softmax 機率 ≥ τ 時就換字。測了三種接法：

- **span**：前文 + 該節點的注音 + 候選字。這是 D512 原本的用法。
- **full**：前文 + 從該節點到句尾的注音 + 候選字 + 後面的文字。
- **疊加**：b = enc + λ·(q35 + w·D512)。

注音照我們的打字習慣標：輕聲用 ˙，一 一律標ㄧ。manifest 裡的 `neutral_tolerant_last`（句尾語助詞可以打一聲）沒有用上，對 D512 略為不利。候選裡有 D512 字表外的字時，照 model card 的作法整題不改，dev 1,104 個 request 中有 15 個是這樣。

程式在 `tools/d512.py`、`tools/evalpipe.py`。

## 4. 結果

### 4.1 dev（500 句 Common Voice，4,352 字；用 repo fixture 重建的決策流程，二折交叉驗證）

| 設定 | 字元／整句 | 跟現行比（修好／改壞字數） |
|---|---|---|
| 現行 q35（λ2 τ.5，就是在這組 dev 上調出來的） | 96.39% / 77.0% | — |
| D512 span，官方 λ2 τ.5 | 96.09% / 75.0% | 變差 |
| D512 span，交叉驗證 | 96.25% / 76.4% | +21 / −27 |
| D512 整句，交叉驗證 | 96.14% / 75.6% | +22 / −33 |
| q35 + D512 span，交叉驗證 | 96.55% / 78.4% | +10 / −3 |
| q35 + D512 整句，交叉驗證 | 96.30% / 76.4% | +17 / −21 |

- 只看模型本身：正確答案在前 3 名的 1,068 個 request 裡，q35 選對 963 個，D512 span 944 個，D512 整句 957 個。
- decoder 這一步最多只能救回 100 個字。

### 4.2 dev（離線完整流程，`results/dev_variants.log`、`full_dev.log`、`grid_dev.log`）

| 設定 | 字元／整句 |
|---|---|
| 現行 q35 span | 96.35% / 76.8% |
| D512 span λ2 τ.5 | 96.09% / 75.2% |
| D512 span＋依序前文 | 96.16% / 75.4% |
| D512 整句 λ1 | 96.37% / 76.2% |

D512 不論單獨用、span 或整句，都不比 q35 好。疊加則穩定多 0.1 到 0.2pt。

- D512 在新聞組的提升比較大，跟它的訓練語料以新聞為主一致。
- 在「在／再」上，D512 沒有額外幫助。

### 4.4 個案

**「那週是馬丁路德金連假」**（使用者回報）：

- 整句排序時，D512 把正確答案排第一（前文「15」：−2.6，下一名是「那周是…」−2.8）。
- 但流程裡的斷詞已經把 ㄐㄧㄣ-ㄌㄧㄢˊ 定成「金蓮」，「連假」不在任何節點的候選裡，所以不管怎麼接 D512 都修不好：

  | 接法 | 輸出 |
  |---|---|
  | D512 取代 decoder | 那周市馬丁路德金蓮價 |
  | D512 取代 decoder＋依序前文 | 那周是馬丁路德金蓮駕 |
  | 設定 E | 那州市馬丁路德金蓮價 |

- 單看一格：前文是「那周」時，「是」−0.05、「市」−6.86；前文是「那州」時，「是」−0.88、「市」−0.79，幾乎平手。這說明「是→市」是因為前文已經錯了，所以後來才加了「依序前文」。

**「會再加以討論」**：

| | 會再 | 會在 |
|---|---|---|
| D512 只看這兩個字 | −1.40 | −0.32 |
| D512 看整句 | −0.10 | −3.10 |

- 跟 q35 一樣，只看左文時分不出「再」，要看到後面的「加以討論」才行。

**dev 的 ㄗㄞˋ（36 個，其中「再」只有 4 個）**：

- 整句打完：現行 35/36，D512（左文＋ㄗㄞˋ）31/36。
- 分段送出：現行 31/36，D512 32/36。
- 樣本太少，不能下結論。

### 4.5 成本

- 執行：只有 ONNX CPU 版本。這台評估機器 4 個 thread、onnxruntime 1.31，每個 span request（3 個候選）P50 10.3 ms、P95 15.6 ms。CPU 型號不明，也沒在 Mac 上量過。
- 要放到 ANE 上得先轉成 Core ML。coremltools 已經不直接吃 ONNX，要先轉回 PyTorch，ANE 放置率未知。
- 檔案 130 MB（fp32），轉 fp16 約 65 MB。
- 字表外的字會讓整題不改。

### 4.6 D512 單獨解碼（不用 encoder、不用詞庫斷詞；事後追加，沒有事先登記）

- **做法**（`tools/d512_beam.py`）：
  - 把 ONNX 計算圖內部的 `log_softmax`（下一個字在整個字表上的分布）接成第二個輸出。
  - 由左到右逐字解碼，beam 寬度 5。每個音節只允許 data.txt 裡該讀音的單字 unigram。
  - 前文為空。沒有調任何參數。
  - 5 條 beam 用樹狀遮罩放進同一次運算，跟逐條算的分布最大差 1e-5。
- **測試資料**：跟 4.3 節同一份新測試集。分析程式是 `tools/analyze_d512only.py`。

| 一般句子，字元／整句 | 聊天 | 新聞 |
|---|---|---|
| B 現行 app | 96.10% / 71.1% | 96.05% / 70.2% |
| D 整句打分＋雙胞胎詞 | 96.44% / 73.8% | 96.39% / 72.6% |
| E D＋0.25·D512 | 96.59% / 74.9% | 96.64% / 74.2% |
| **只用 D512** | **96.44% / 74.9%** | **97.53% / 80.5%** |
| 只用 D512 − D | +0.00pt [−0.36, +0.36] | **+1.14pt** [+0.80, +1.48] |
| 只用 D512 − B | +0.34pt [−0.01, +0.70] | +1.47pt [+1.11, +1.82] |

| ㄗㄞˋ 位置 | 聊天：「再」選對 / 「在」錯成「再」 | 新聞：「再」選對 / 「在」錯成「再」 |
|---|---|---|
| B | 919/1353 (68%) / 31 | 812/1234 (66%) / 5 |
| D | 1082/1353 (80%) / 34 | 971/1234 (79%) / 2 |
| 只用 D512 | 1131/1353 (84%) / 48 | 989/1234 (80%) / 11 |

**解讀：**

- 放在 decoder 位置時，D512 只能從 encoder 前 3 名、詞庫斷好的格子裡挑字，所以看起來比 q35 弱。單獨解碼不受這兩個限制，聊天組追平整套流程，新聞組（D512 的訓練語料領域）大幅領先。
- 「再」選得更積極：「再」選對的變多，但「在」被錯改成「再」也變多，聊天組從 34 增加到 48。
- 例外：「那週是馬丁路德金連假」單獨解碼得到「那州市馬丁路德金廉價」。整句排序時正確答案是第一，但 beam 寬度 5 在前半段就把正確答案淘汰了。

**限制：**

- 速度：這台機器上每句 0.2 到 0.5 秒，因為沒有 KV cache，每一步都從頭重算整個序列。輸入法每按一鍵都要更新，必須做增量解碼（KV cache）並放到 ANE 上。
- 功能：只用 D512 會失去小麥注音建立在詞庫斷詞上的功能，包括使用者詞庫、詞彙替換、選字記憶、候選窗。
- 事後追加：沒有事先登記。但這組測試沒有調參數，算是用新測試集看第一次。

## 5. 下一步與什麼時候再評估

- **建議的下一步：「兩案並陳」混合版。**
  1. 同一個 buffer 同時跑現行流程（設定 D）和 D512 單獨解碼。
  2. 兩句不同時，用「D512 整句分數 + α·encoder 分數」挑一句，必要時加 margin。
  3. α 和 margin 先在 dev 上調，再在新測試集上驗證一次。
  4. D512 那一路需要 Core ML 或 ANE 版本、KV cache 增量解碼，並在 Mac 上量延遲。目標是背景執行，不影響按鍵回應，跟現行 decoder 一樣。
- 也可以在 beam search 裡加入詞庫或 encoder 的分數，例如 b = D512 + β·encoder，或保留使用者詞庫的約束，讓 D512 那一路也能用上小麥注音的功能。
- 「在」被錯改成「再」變多這件事，混合版要特別盯：門檻或 margin 要讓「在→再」的改壞數不比 D 多。
- 0c 如果釋出更強的新版，或以聊天語料訓練的版本，用同一套工具重跑 4.3 和 4.6 節。
- 標點模型可以另外評估，跟 reranker 無關。
